# 09 故障排查

- **适用版本**：v12.1.6
- **适用读者**：处理线上问题的运维人员与技术支持
- **前置条件**：能访问日志、管理后台与基础运行环境信息

本章按常见现象组织排查路径，覆盖账号、验证码、任务执行、队列、图片访问、依赖组件与回调等环节。排查时先确认现象与影响范围，再结合日志与后台状态逐层缩小问题，不要直接修改生产配置试错。

## 快速分诊
1. 确认影响范围：单账号、单渠道、单节点，还是全部任务；先判断是否与一次发布、配置保存或网络变更同时发生。
2. 确认请求层结果：连接失败、502/504、429、403、业务失败还是任务失败；不同层级的处理路径不同。
3. 确认依赖状态：数据库是否降级、Redis 是否被禁用、账号是否在线、队列是否堆积。
4. 固定证据：记录任务 ID、渠道 ID、时间点与日志片段，再决定重试、重连、重启或回滚。
5. 任何配置修改前先备份，并优先在单节点或测试账号上验证，确认有效后再推广。

| 返回/现象 | 常见含义 | 优先检查 |
| --- | --- | --- |
| 429 | 普通限流命中 | IP 规则、客户端重试频率 |
| 403 | 黑名单限流或权限不足 | 黑名单、管理员角色、账号状态 |
| 502 / 504 | 上游不可达或超时 | 应用存活、端口映射、代理超时 |
| 200 且业务失败 | 参数、队列、账号或上游问题 | 错误文案、日志、账号与队列 |

```bash
curl -fsS -H "Authorization: {token}" http://127.0.0.1:8080/mj/task/{taskId}/fetch
grep -n "{taskId}" logs/log.txt
```

## 1. 账号无法上线 / 启动即禁用
**现象**：账号列表显示禁用，`DisabledReason` 有值；后台看不到运行实例；任务提示「无可用的账号实例」；刚启用后很快又变成禁用。
**可能原因**：
- Token 失效、UserAgent 与账号不匹配、代理或 DNS 不通。
- GuildId/ChannelId 填错，账号没有加入对应服务器或频道。
- 账号被风控、订阅过期、额度耗尽，或触发 Cloudflare 验证。
- 当前时间不在 `WorkTime` 或 `FishingTime` 内，系统按设计不创建实例。
- 数据库或 Redis 异常，初始化过程抛错。
**排查步骤**：
1. 在日志中按渠道 ID 检索 `初始化失败`、`自动登录`、`账号用量已经用完`，记录异常原文。
2. 打开账号详情，核对渠道 ID、服务器 ID、启用状态、禁用原因、工作时间与摸鱼时间。
3. 对照当前时间确认是否处于允许时段；非工作/摸鱼时间会释放已有实例，这是正常行为。
4. 在容器内用同一代理访问 Discord 接口，确认 DNS、TLS、代理与出站网络正常。
5. 执行「同步信息与设置」；仍失败时再执行重连，观察初始化日志。
**处理方式**：修正凭据、频道与代理后重新启用；订阅或额度问题需续费/换号；风控问题按第 2 节处理。批量启用只写入启用状态，后台例行检查最多约 1 分钟后才会启动实例，不要连续重复启用。重连会更新账号、释放旧实例并重新启动，适合凭据变更后使用。

## 2. Cloudflare 人机验证
**现象**：账号被锁定，禁用原因显示「CF 自动验证中...」或「CF 人工验证...」；日志出现 `CF 验证`、`Action required to continue`；相关任务卡住或失败。
**可能原因**：
- 账号触发官网风控，需要人工完成 challenge。
- 未配置验证服务器，或 `CaptchaServer`、`CaptchaNotifyHook`、`CaptchaNotifySecret` 不一致。
- 自动验证未同时满足：开启自动验证、配置 2Captcha 密钥、Redis 可用。
- 出口 IP 被污染，或代理频繁切换。
**排查步骤**：
1. 查看账号的 `CfUrl`、`CfHashUrl`、`CfHashCreated` 与禁用原因。
2. 检索日志中的验证 URL；没有配置验证服务器时，系统会尝试通过邮件发送链接。
3. 检查验证服务器地址是否可达，回调地址与密钥是否匹配。
4. 确认自动验证开关、2Captcha 密钥与 Redis 状态；自动验证需要这三项同时满足。
5. 确认是否配置了触发上限，超过上限后账号可能被自动禁用。
**处理方式**：优先人工打开验证链接完成 challenge，完成后解锁并重连；配置稳定的验证服务与回调密钥；更换干净的出口 IP；自动验证不可用时不要反复重试，避免触发更高风控。验证通过后仍需观察账号是否能正常同步信息。

## 3. 任务一直 SUBMITTED
**现象**：任务状态长期为 `SUBMITTED`，进度 `0%`，没有后续消息；客户端轮询不到结果。
**可能原因**：
- 提交请求成功，但 Discord 消息未送达或未收到 `MESSAGE_UPDATE`。
- WebSocket 断开、重连失败，或账号处于锁定/风控状态。
- 频道 ID 错误，机器人不在目标频道。
- 任务入队后工作线程未消费，Redis 队列或实例异常。
- 服务重启后任务未恢复到运行态。
**排查步骤**：
1. 查看任务的 `InstanceId`、`SubmitTime`、`StartTime`、`MessageId`、`MessageIds`、`Progress`、`State`。
2. 检索日志中的 `SubmitImagine`、`任务执行结束`、`用户 WebSocket 连接失败`、`重连`。
3. 检查账号是否在线、是否 `Lock`、是否有禁用原因。
4. 检查 Redis 队列长度与消费情况，确认实例后台循环仍在运行。
5. 若任务已超过账号 `TimeoutMinutes`，按第 4 节判断是否已进入超时。
**处理方式**：先重连账号并触发同步，等待一个超时周期；确认无法恢复后通过任务取消接口结束任务并重新提交。取消会把未完成任务置为失败（原因「取消任务」），不是 `CANCEL` 状态，客户端需按失败处理。不要直接改数据库状态，否则运行态与库内状态会不一致。

## 4. 任务超时 / 失败
**现象**：任务状态为 `FAILURE`，`FailReason` 有值；常见文案包括「执行超时 X 分钟」「任务提交超时」「任务超时，自动取消」「实例不可用」「可能包含敏感词」「服务异常，请稍后重试」。
**可能原因**：
- 生成耗时超过账号 `TimeoutMinutes`，默认 5 分钟。
- 任务在队列等待过久，超过超时时间的 12 倍仍未开始。
- 账号中途掉线、额度耗尽、订阅失效或被上游限制。
- 提示词违规、参数非法、图片链接无效。
- 上游返回 5xx、超时或结果过滤。
**排查步骤**：
1. 读取 `FailReason`，区分提交阶段、执行阶段与队列阶段。
2. 对比 `SubmitTime`、`StartTime`、`FinishTime`，判断耗时发生在排队还是执行。
3. 检查任务所属账号的状态、额度、模式与是否在任务期间被禁用。
4. 检索日志中的上游错误，如 `Invalid prompt`、`Banned prompt detected`、`Credits exhausted`、`Queue full`、`Blocked`、`Subscription required`。
5. 检查提示词与输入图片，确认没有违规词、失效链接或超出参数范围。
**处理方式**：修正提示词、图片或账号后重新提交；额度/订阅问题续费或换号；网络或上游瞬时错误可退避后重试。不要无脑调大超时，先确认是排队、账号还是上游问题。Discord 任务没有自动重试，悠船可按需开启失败自动重试；重试必须控制频率，避免重复扣费与任务风暴。

## 5. 队列已满
**现象**：提交接口返回「提交失败，队列已满，请稍后重试」；首页并发/队列概览显示可用队列为 0；任务无法入队。
**可能原因**：
- 单账号 `QueueSize` 或 `RelaxQueueSize` 已达上限。
- 账号掉线、并发被下调，消费能力下降。
- 流量突增，或慢任务占满工作线程。
- 放大任务积压（放大队列允许溢出，通常不是此错误）。
**排查步骤**：
1. 确认返回文案与 HTTP 状态，排除限流导致的 429/403。
2. 查看账号的 `QueueSize`、`RelaxQueueSize`、`CoreSize` 与在线状态。
3. 在 Redis 中查看 `queue:fast:{channelId}`、`queue:relax:{channelId}`、`queue:describe:{channelId}` 的长度。
4. 检索日志中的 `队列已满`，确认是提交前检查还是入队失败。
5. 检查工作线程是否卡在慢任务、账号是否被锁定。
**处理方式**：先让客户端退避重试；恢复掉线账号；按容量评估增加账号或适度提高队列上限（Excel 导入限制 CoreSize ≤12、QueueSize 1–100；账号表单仅校验 ≥1，服务端没有同样上限）。不要只调大队列而不提升消费能力，否则只是把压力堆到 Redis。账号的 `MaxQueueSize` 是兼容字段，当前实际限流以 `QueueSize`/`RelaxQueueSize` 为准。

## 6. 图片 404 / 加载慢
**现象**：任务成功但图片打不开，返回 404/403；客户端加载缓慢或跨域失败；历史图片突然失效。
**可能原因**：
- `ImageStorageType=NONE`，返回的是上游临时链接，已过期或受防盗链限制。
- 本地存储文件缺失，附件目录未挂载或被清理。
- 自定义 CDN 域名错误、回源失败或缓存了错误响应。
- 对象存储桶为私有读、Key 不存在或跨域未配置。
- 反向代理未正确转发静态资源，或磁盘已满。
**排查步骤**：
1. 取图片 URL，确认主机是上游 CDN、应用域名还是自定义 CDN。
2. 对照 `ImageStorageType` 与本地存储/对象存储配置。
3. 本地存储时检查 `wwwroot/attachments`、`wwwroot/ephemeral-attachments` 中是否存在对应文件，容器挂载是否生效。
4. 从外部网络 `curl -I` 图片地址，区分 404、403、超时与证书错误。
5. 检查 CDN 回源日志、对象存储对象列表与应用日志中的「文件不存在」。
**处理方式**：恢复挂载与文件；修正 CDN 域名与回源；对象存储改为可读或启用预签名；为高流量场景前置 CDN。历史链接不会因切换存储自动改写，需要保留旧域名或按规则迁移。上游链接场景应开启结果落地存储，不要依赖临时 URL。

## 7. 数据库连接失败降级 SQLite
**现象**：启动时间明显变长；日志出现 10 秒、60 秒、360 秒重试；最终提示「切换为 SQLite 数据库」；后台数据像是「空了」。
**可能原因**：
- 数据库宕机、网络/防火墙不通、连接账号或口令有误、库名错误。
- 账号缺少建表/索引权限，或连接数耗尽。
- TLS、时区、字符集或驱动参数不兼容。
- 启动时数据库尚未就绪，重试次数用尽。
**排查步骤**：
1. 检索日志中的 `数据库连接失败`、`数据库类型`、`切换为 SQLite`，确认重试与降级。
2. 用数据库客户端从应用所在网络执行 `SELECT 1`，核对连接串、库名与权限。
3. 检查数据库最大连接数、磁盘空间与慢查询。
4. 在后台执行「验证数据库连接」，不要直接反复保存配置。
5. 确认降级期间是否产生了新数据（会写入本地 SQLite）。
**处理方式**：修复数据库后重启应用；降级状态只保存在内存，不会自动写回 `data/mj.json` 或 Consul，重启后才会重新连接原数据库。降级期间写入 SQLite 的数据需要先导出/合并再切回。SQLite 路径固定为 `data/mj_sqlite.db`；降级时需确认管理员令牌已轮换、管理端未暴露。

## 8. Redis 不可用 / 设置无法保存
**现象**：启动日志提示「Redis 连接失败，已自动禁用 Redis 功能」；缓存与分布式锁退化为单机；保存系统设置失败；任务入队/消费异常；例行检查日志出现「系统配置错误，请检查Redis配置」。
**可能原因**：
- Redis 宕机、密码错误、ACL 限制、网络不通或达到最大连接数。
- 连接串格式错误，或未开启 `EnableRedis`。
- 内存打满、持久化阻塞、主从切换。
- 多节点使用了不同的 Redis。
**排查步骤**：
1. 用 `redis-cli` 带认证执行 `PING`，确认返回 `PONG`。
2. 检索启动日志与保存设置时的错误提示，区分连接失败与配置校验失败。
3. 检查连接串、密码、数据库序号、超时与 TLS 配置。
4. 查看 Redis 内存、连接数、慢日志与主从状态。
5. 确认所有节点连接同一 Redis，且任务队列 Key 有消费。
**处理方式**：恢复 Redis 后重启应用以重新启用；自动禁用只保存在内存，不会自行恢复。保存系统设置前必须保证 Redis 可用，否则会因「必须配置 Redis 模式」或连接失败被拒绝。任务队列本身依赖 Redis，所谓降级只覆盖缓存与锁，不能把无 Redis 当成完整可用的单机模式。

## 9. 回调未收到 / 重复
**现象**：任务完成但业务方没有收到 POST；或同一任务收到多次、状态顺序错乱。
**可能原因**：
- 没有配置全局 `NotifyHook`，任务也没有携带 `notifyHook`。
- 回调地址超过长度限制、DNS/TLS 不通、被防火墙拦截或需要鉴权。
- 对端返回非 2xx 或响应过慢。
- 同一状态重复推送被去重；服务重启、重连或重新提交后再次推送。
**排查步骤**：
1. 查看任务属性中的 `notifyHook`，确认是任务级还是全局配置。
2. 检索日志 `Notify task change fail`，记录状态码与响应片段；需要观察成功推送时，可临时把日志级别调到 Debug 再检索 `Push task change`。
3. 从应用容器内 `curl` 回调地址，确认网络与证书可达。
4. 对比收到的 `status`、`progress`，确认是否只有更高进度才推送。
5. 检查对端是否按任务 ID 做了幂等。
**处理方式**：补齐回调地址并保证公网/内网可达；对端快速返回 2xx，把业务处理异步化；按 `任务ID + 状态 + 进度` 做幂等。回调是「尽力推送」，没有自动重试，不能假设 exactly-once；服务重启或任务恢复后可能再次收到同一终态，业务方必须可重入。

## 10. 悠船账号登录 / 额度问题
**现象**：悠船账号无法上线或频繁禁用；登录长时间无结果；任务提示额度不足或直接失败。
**可能原因**：
- 令牌/登录凭据失效，账号未标记为悠船账号。
- 快速或慢速额度耗尽、订阅到期、日限额达到上限。
- 自动登录超过 10 分钟未回调，被视为登录超时。
- 出口网络不稳定，或图片下载未使用合适的线路。
**排查步骤**：
1. 查看账号的 `IsYouChuan`、`DisabledReason`、`LoginMessage`、`YouChuanExpire`。
2. 核对 `YouChuanFastRemaining`、`YouChuanRelaxDailyLimit` 与各重置时间。
3. 检索日志中的登录、额度和上游错误；确认是否开启悠船功能。
4. 检查到悠船服务的网络与代理，必要时执行同步信息。
5. 确认是否开启了优先慢速、失败重试等策略，避免把策略误判为故障。
**处理方式**：更新凭据后重连；额度不足时等待重置或调整账号；网络抖动可开启失败自动重试，但必须控制频率；仅在阿里云上海地域且确有需要时开启内网下载。登录过程中不要重复触发，超过 10 分钟应重新发起而不是无限等待。

## 11. 官网账号 Cookie 失效
**现象**：官网账号被禁用或任务全部失败；日志出现 401/403、验证失败或订阅提示；账号无法同步信息。
**可能原因**：
- Cookie 过期、被踢下线，或账号在其他设备登录。
- 出口 IP 变化、UserAgent 与 Cookie 不匹配。
- 触发 Cloudflare 验证或账号风控。
- 订阅过期、额度耗尽或功能未开通。
**排查步骤**：
1. 查看账号的 `IsOfficial`、`Cookie`、`UserAgent`、`DisabledReason`。
2. 检索日志中的 401/403、`CF 验证`、订阅与额度错误。
3. 确认出口 IP 是否稳定，代理是否频繁切换。
4. 检查 `CfUrl`、`CfHashUrl` 是否存在待处理验证。
5. 用同一网络与 UserAgent 验证 Cookie 是否仍有效。
**处理方式**：重新获取 Cookie 并保持 UserAgent、IP 稳定；完成 Cloudflare 验证后解锁重连；订阅/额度问题续费或换号；凭据更新后执行同步信息与设置。不要把失效 Cookie 反复重试，容易加速风控。

## 12. 视频任务失败
**现象**：提交返回「视频功能未启用」或「无可用的账号实例」；任务失败；视频 URL 为空；视频合并失败。
**可能原因**：
- 未开启视频功能，或账号不具备视频/高清视频/慢速视频能力。
- Niji 视频扩展未开启 Remix。
- 首帧/尾帧图片链接不可达，或格式不支持。
- 运行环境缺少 `ffmpeg`/`ffprobe`，或合并质量/磁盘空间不足。
- 生成时间超过账号超时。
**排查步骤**：
1. 检查 `EnableVideo`、`EnableVideoMerge`、`VideoMergeQuality`。
2. 核对账号 `IsHdVideo`、`IsRelaxVideo`，以及请求是否要求高清。
3. 检查提示词是否包含 `--video`，Niji 扩展是否满足 Remix 条件。
4. 检索日志中的下载、转码、合并错误；确认 `ffmpeg`/`ffprobe` 可执行。
5. 查看任务 `VideoUrl`、`VideoUrls`、`FrameCount` 与失败原因。
**处理方式**：开启功能并使用具备能力的账号；修正输入图片与网络；安装或修复 ffmpeg；磁盘不足时清理；合并失败可临时关闭视频合并验证主流程。视频生成耗时较长，必要时单独评估超时，不要影响普通绘图任务。

## 13. 反向代理 502 / 超时
**现象**：客户端收到 502、504、413；上传大图失败；请求长时间无响应；健康检查偶发失败。
**可能原因**：
- 应用未启动、端口映射错误或容器重启中。
- 代理读超时/发送超时过短，覆盖不了生成与上传耗时。
- 请求体超过代理或 Kestrel 限制。
- DNS、TLS、Keep-Alive 或上游地址配置错误。
**排查步骤**：
1. 在应用主机执行 `curl -fsS http://127.0.0.1:8080/health`，确认上游存活。
2. 检查容器端口映射（示例 `8086:8080`）与监听地址。
3. 查看代理错误日志，区分连接拒绝、超时与请求体过大。
4. 对比 `client_max_body_size`、`proxy_read_timeout`、`proxy_send_timeout` 与 Kestrel 请求体限制。
5. 用大图与小请求分别验证，确认是体积问题还是耗时问题。
**处理方式**：恢复应用与端口映射；为提交、上传接口设置足够超时；按需提高请求体上限；开启健康检查与自动重启。不要把超时压得比正常生成时间还短，否则会把成功任务误判为 504。

## 14. 升级后配置不一致
**现象**：升级后设置回到默认值，注册/访客被打开；数据库类型变化；账号或任务「消失」；配置版本冲突。
**可能原因**：
- `data` 目录未挂载或挂载路径变化，新容器使用空目录。
- 升级覆盖了 `data/mj.json`，或恢复了旧备份。
- 启用 Consul 时远程 KV 与本地缓存版本不一致。
- 提交的 Revision 过期，保存被拒绝。
- 数据库连接失败后降级 SQLite，看起来像数据丢失。
**排查步骤**：
1. 对比容器挂载与 `data/mj.json` 内容，确认是否为新生成的默认配置。
2. 检查 Consul KV 的配置与 Revision，确认当前节点加载的是哪一份。
3. 查看启动日志中的数据库类型、Redis 状态与降级记录。
4. 核对账号数、任务数与升级前备份。
5. 保存设置时若提示版本过期，先重新加载远程配置，不要强行覆盖。
**处理方式**：恢复正确挂载与备份配置；Consul 场景先对齐 KV 再保存；数据库结构变更导致不兼容时按回滚流程恢复数据库；立即关闭被误开的注册、访客与演示模式，并重置管理员 Token。升级前完成备份与挂载核对，是避免此类问题的最有效手段。
