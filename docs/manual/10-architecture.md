# 10 架构说明

- **适用版本**：v12.1.6
- **适用读者**：需要理解内部机制、准备二次开发或深度排障的工程师
- **前置条件**：熟悉 .NET 8 应用的基本结构，了解异步任务与消息队列概念

本章从整体链路出发，说明一次请求如何进入系统、任务如何流转、账号如何被选择，以及队列、分布式部署、存储与回调之间的关系。目标是给出可支撑排障与二次开发的机制视角，不展开具体代码实现。

## 阅读顺序
1. 先看「整体组件」建立组件边界，再看「请求链路」理解一次提交如何落到队列。
2. 然后看「账号选择」「队列与工作线程」「任务状态机」，理解任务为什么等待、执行为什么失败。
3. 最后看「存储与回调」「分布式协作」「Consul」「失败与降级」，用于排障与容量设计。

## 请求链路
### 入口与中间件
请求先经过 Kestrel，再按顺序进入静态文件、CORS、路由、鉴权、限流与控制器。`SimpleAuthMiddleware` 对 `/health`、`/debug` 放行；演示模式跳过鉴权；带匿名标记的接口不要求登录；`/mj/admin` 要求管理员角色；普通接口在未开启访客时要求有效用户。`RateLimitingMiddleware` 对匿名接口、管理员与白名单用户跳过，其余按 IP、/24、/16 规则计数，普通限流超限返回 429，黑名单超限返回 403 并按配置封锁。

### 参数校验与鉴权
控制器先校验必填字段、长度、base64/链接格式与用户配额，再创建任务对象。任务会记录用户、客户端 IP、动作、提示词、速度模式、`AccountFilter` 与 `notifyHook`。用户级并发、日限额与队列限制在提交阶段检查，超出时直接返回业务失败，不进入队列。

### 任务入队与响应
`TaskService` 解析提示词、处理翻译与违规词、确定动作类型，然后调用 `AccountService.ChooseInstance` 选择实例，把任务写入该账号的 Redis 队列。入队成功后立即返回任务 ID 与状态，客户端通过任务查询接口轮询，或等待回调。入队失败（例如队列已满）会删除已保存的任务记录，避免产生永远无法执行的脏数据。

## 账号选择
### 候选账号筛选
选号前会按请求条件过滤：账号是否启用、是否存活、是否支持 MJ/Niji、是否支持 Blend/Describe/Shorten、是否为悠船/官网、是否满足高清视频、是否属于指定垂直领域或指定实例；同时排除调用方显式排除的账号。过滤后一次性读取候选账号的队列与并发快照，避免逐个账号访问 Redis。

### 排队与占用
选号规则由 `AccountChooseRule` 决定：

| 规则 | 行为 |
| --- | --- |
| `BestWaitIdle` | 优先选择队列利用率最低的账号，利用率相同则随机 |
| `Random` | 在可用账号中随机 |
| `Weight` | 按账号权重分配 |
| `Polling` | 轮询 |
| `AccountFill` | 优先打满最早创建的账号，再按时间、并发与队列判断 |

选定账号后还要确认该账号在目标速度模式下仍有并发与队列空间；悠船会同时考虑快速与慢速两套队列。

### 选择结果与回退
如果没有可用实例，提交直接失败并返回「无可用的账号实例」。某些动作允许在多个速度模式间回退：先尝试请求模式，再尝试其他允许模式；悠船开启「优先慢速」时，可能在快速/极速请求前插入一次慢速尝试。最终模式会写回任务的 `Mode`，后续队列与计数都按该模式执行。

## 队列与工作线程
### 队列结构
每个账号实例拥有独立队列，Redis Key 以账号渠道 ID 区分：

| 队列 | Key 形式 | 用途 |
| --- | --- | --- |
| 快速/默认 | `queue:fast:{channelId}` | 普通绘图、动作任务 |
| 慢速 | `queue:relax:{channelId}` | 悠船慢速任务 |
| 图生文 | `queue:describe:{channelId}` | Describe 任务 |
| 放大 | `queue:upscale:{channelId}` | U 放大，允许溢出 |

入队使用分布式锁保护容量检查，出队使用阻塞弹出并受 Redis 并发锁与全局并发锁双重约束。

### 并发控制
每个账号的后台循环先检查队列长度，再申请全局并发配额与账号级 Redis 并发配额，成功后出队，把实际执行投递到全局 `BackgroundTaskExecutor`。执行完成后释放锁并发出通知。账号级 `CoreSize` 控制同时执行数，`QueueSize` 控制等待数；全局 `CONCURRENT` 控制单节点总并行，`0` 与 `-1` 均按 1280 处理。

### 不可用时的行为
任务队列依赖 Redis；Redis 不可用时缓存与分布式锁会退化为内存模式，但队列无法正常工作，例行检查也会跳过。队列满时提交返回失败；账号离线或并发被占满时任务会留在队列等待，直到超时或账号恢复。

## 任务状态机
### 状态流转
```text
NOT_START ──入队/提交成功──▶ SUBMITTED ──收到进度──▶ IN_PROGRESS ──完成──▶ SUCCESS
     │                          │                       │
     │                          ├──需要弹窗/Remix──────▶ MODAL ──确认──▶ SUBMITTED
     │                          │                       │
     └────────超时/异常─────────┴───────────────────────┴──▶ FAILURE
     │
     └──取消──────────────────────────────────────────────▶ FAILURE / CANCEL
```

| 状态 | 值 | 含义 |
| --- | --- | --- |
| `NOT_START` | 0 | 已创建、尚未提交到上游 |
| `SUBMITTED` | 1 | 已提交，等待上游消息 |
| `IN_PROGRESS` | 3 | 上游返回进度 |
| `FAILURE` | 4 | 失败、超时或取消 |
| `SUCCESS` | 5 | 成功并完成结果处理 |
| `MODAL` | 6 | 等待弹窗确认（Remix、局部重绘等） |
| `CANCEL` | 7 | 取消 |

### 终止态与失败态
`SUCCESS`、`FAILURE`、`CANCEL` 为终止态。失败原因会写入 `FailReason`，常见来源包括上游错误、敏感词、实例不可用、提交或执行超时、服务异常。管理端取消未完成任务通常写入 `FAILURE` 并记录「取消任务」，不要假设一定是 `CANCEL`。

### 超时与重试边界
任务从 `SUBMITTED`/`IN_PROGRESS` 开始计时，超过账号 `TimeoutMinutes`（默认 5 分钟）标记失败；`NOT_START` 任务按 `TimeoutMinutes × 12` 判断提交超时。后台例行检查还会把「1–6 小时前未开始且账号实例已不可用」的任务标记失败。Discord 任务没有内置自动重试，悠船可按配置开启失败重试；重试责任主要在调用方。

## 结果回收与存储
- Discord 通过 WebSocket 接收消息创建/更新事件，解析进度、按钮、embeds 与最终图片；悠船与官网通过轮询更新状态。
- 每次状态或进度变化都会保存任务并按规则触发回调；只有状态或进度更高时才推送，避免重复。
- 成功后根据配置下载结果：`ImageStorageType` 决定不存储、本地、OSS、COS、R2 或 S3；本地写入 `wwwroot/attachments` 与 `wwwroot/ephemeral-attachments`。
- 结果 URL 可经自定义 CDN 重写；历史 URL 不会因切换存储自动变化。
- 视频任务还会处理视频下载、合并与截帧，依赖运行环境的 `ffmpeg`/`ffprobe`。

## 回调投递
任务级 `notifyHook` 优先于全局 `NotifyHook`；未配置时不会推送。回调以 POST 发送完整 `TaskInfo` JSON（camelCase，枚举为字符串），包含任务 ID、状态、进度、结果 URL、失败原因等字段。推送前用「状态 + 进度」比较，只允许更高进度通过；任务进入成功或失败终态后清理去重记录。推送失败只记录日志，没有自动重试；服务重启或任务恢复后可能再次推送同一终态，接收方必须按任务 ID 幂等处理。

## 分布式协作
- 多节点共享同一 Redis：任务队列、并发计数、分布式锁、配置变更广播与取消通知都通过 Redis 完成。
- 多节点共享同一数据库：任务、账号、用户与配置持久化在同一库；节点本地只保留缓存。
- 账号实例在各节点独立运行，队列按账号渠道 ID 共享，因此同一账号的任务可能被任一节点消费。
- 配置变更通过发布订阅通知其他节点重新加载；取消、删除、重启等操作也会广播。
- 服务重启后，账号会把最近 12 小时内未完成的任务重新加入队列，避免任务永久丢失。

## Consul
启用 Consul 后，它同时承担配置中心与服务发现：

| 用途 | Key/配置 | 行为 |
| --- | --- | --- |
| 共享配置 | `{ServiceName}/setting` | 启动从 leader 一致性读取；本地 `data/mj.json` 仅作缓存与应急启动 |
| 配置保存 | 同上 | 使用 CAS + `Revision` 乐观锁，版本不一致直接失败 |
| 版本对齐 | `{ServiceName}/version` | 节点版本低于注册中心时可触发更新并退出等待重启 |
| 服务注册 | `ServiceName`、`ServicePort` | 注册实例并写入健康检查地址 |
| 健康检查 | 默认 `/health` | 间隔 10 秒、超时 5 秒、严重失联 1 分钟后注销 |

运行时重载只接受 Consul 的远程配置；Consul 不可用时保留当前内存配置，不回退到本地缓存，避免节点回滚到旧配置。

## 失败与降级

| 场景 | 系统行为 | 影响 |
| --- | --- | --- |
| 数据库连接失败 | 10s/60s/360s 重试，仍失败则运行时切 SQLite | 数据看起来「变空」；降级状态只在内存，不写回配置 |
| Redis 连接失败 | 启动 Ping 失败后禁用 Redis | 缓存/锁退化单机；队列与例行检查受影响，不能视为完整可用 |
| 队列已满 | 提交返回失败并删除未入队记录 | 调用方需退避重试或扩容 |
| 账号初始化失败 | 自动 `Enable=false` 并写 `DisabledReason` | 该账号不参与选号；批量启用后最多约 1 分钟巡检启动 |
| 上游超时/错误 | 任务标记失败并记录原因 | 需修正提示词、账号或网络后重提 |
| 回调失败 | 记录 Warning，不自动重试 | 接收方需补偿或主动查询任务 |
| Consul 不可用 | 启动用本地配置，运行时保留当前配置 | 共享配置无法保存；各节点可能配置不一致 |

降级设计的共同原则是「不把运行时异常写回共享配置」：数据库与 Redis 的降级状态只影响当前进程，管理员显式保存才会写入本地文件或 Consul。这也意味着恢复依赖后通常需要重启节点，不能假设系统会自动回到正常模式。
